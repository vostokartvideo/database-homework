# Системы хранения и обработки данных

## Задание 1. СУБД

### 1.1. Бюджетирование проектов и финансовая аналитика

**Ответ:**

Для бюджетирования проектов я бы выбрал реляционную СУБД PostgreSQL.

Финансовые данные должны иметь строгую структуру и сохранять целостность. В PostgreSQL можно создавать связанные таблицы для хранения проектов, расходов, доходов, сотрудников и бюджетов.

Также PostgreSQL поддерживает транзакции ACID, которые помогают обеспечить корректное выполнение операций с финансовыми данными.

Для формирования отчётов можно использовать SQL-запросы, объединять данные из разных таблиц и рассчитывать финансовые показатели.

### 1.1.* Хеширование стало занимать длительное время. Какое API использовать?

**Ответ:**

Если речь идёт об ускорении повторного получения данных, я бы предложил использовать Redis и его API-команды GET, SET, HGET, HSET.

Redis хранит часто используемые данные в оперативной памяти, поэтому повторное получение результатов может происходить быстрее, чем запросы к основной базе данных.

### 1.2. Лендинги и CRM

**Ответ:**

Для лендингов и CRM можно использовать сочетание двух типов СУБД:

- MongoDB (NoSQL, документная) — для хранения гибких данных лендингов, например различных анкет, параметров рекламных кампаний и дополнительных полей клиентов.

- PostgreSQL (SQL, реляционная) — для CRM, где важно хранить информацию о клиентах, сделках, менеджерах и взаимодействиях между ними.

MongoDB удобна, когда структура данных часто меняется. PostgreSQL подходит для CRM, поскольку обеспечивает связи между таблицами и целостность данных.

### 1.3. Корпоративные нормы, правила и обучающие материалы

**Ответ:**

Для этой задачи я бы выбрал СУБД MongoDB.

Информация может храниться в виде документов, организованных по разделам: строительные нормы, техника безопасности, внутренние инструкции и обучение сотрудников.

Документная модель позволяет удобно хранить материалы с разной структурой, добавлять новые разделы и изменять содержание без постоянного изменения схемы таблиц.

### 1.3.* Можно ли использовать существующую СУБД?

**Ответ:**

Да. Можно использовать PostgreSQL, выбранную ранее для финансового учёта и CRM.

Для базы знаний можно создать отдельную базу данных или схему, где будут храниться категории документов, названия, содержание, даты обновления и права доступа.

Для материалов с нестандартной структурой можно использовать JSONB.

### 1.4. Логистика и построение маршрутов

**Ответ:**

Для работы со связями между объектами я бы выбрал графовую СУБД Neo4j.

В ней можно представить склады, строительные объекты и пункты доставки в виде узлов, а дороги и маршруты — в виде связей между ними.

Графовая модель удобна для поиска путей между объектами и анализа сложных связей.

Например, можно искать короткий путь между складом и строительной площадкой с учётом расстояний или заданной стоимости перемещения

### 1.4.* Можно ли подключить отдел закупок?

**Ответ:**

Да, отдел закупок можно подключить к той же системе, если необходимо анализировать связи между поставщиками, складами, материалами и строительными объектами. Но для учёта закупок, договоров, цен и оплаты лучше использовать PostgreSQL. В этом случае PostgreSQL будет хранить основную информацию о закупках, а Neo4j — использовать необходимые данные для анализа логистических связей.

### 1.5.* Можно ли решить все задачи одной СУБД?

**Ответ:**

Да, для всех перечисленных задач можно использовать PostgreSQL с дополнительными расширениями.

- Финансовый учёт — обычные реляционные таблицы и SQL.

- CRM и лендинги — таблицы и JSONB.

- Корпоративная база знаний — таблицы, JSONB и полнотекстовый поиск.

- Логистика — PostgreSQL с расширениями PostGIS и pgRouting.

## Задание 2. Транзакции

### 2.1. Пополнение баланса мобильного телефона

**Ответ:**

При пополнении баланса необходимо выполнить следующие шесть действий:

1. Проверка данных. Проверить номер телефона, сумму пополнения и наличие достаточных средств на банковском счёте.

1. Начало операции. Создать платёжную операцию с уникальным идентификатором, чтобы отслеживать её выполнение.

1. Списание средств. Банк проверяет и подтверждает списание необходимой суммы со счёта пользователя.

1. Передача информации. Платёжная система отправляет оператору мобильной связи запрос на пополнение баланса.

1. Зачисление средств. Оператор увеличивает баланс телефона и возвращает подтверждение.

1. Завершение операции. Система фиксирует успешное выполнение платежа и уведомляет пользователя.

Если возникла ошибка, операция должна быть обработана таким образом, чтобы пользователь не потерял деньги и не произошло двойного списания.

### 2.1.* Что изменится при автоплатеже?

**Ответ:**

При автоматическом пополнении действия будут практически такими же, но запускать операцию будет не пользователь, а специальный сервис.

1. Проверяется условие автоплатежа — например, наступила установленная дата или баланс опустился ниже заданной суммы.

1. Система проверяет, что автоплатёж активен и пользователь разрешил списание.

1. Создаётся уникальная платёжная операция.

1. Выполняется списание средств.

1. Оператору отправляется запрос на пополнение баланса.

1. После подтверждения результат сохраняется, а пользователь получает уведомление.

## Задание 3. SQL vs NoSQL

### 3.1. Пять преимуществ SQL перед NoSQL

**Ответ:**

1. Строгая структура данных. В реляционных СУБД данные организованы в таблицы со столбцами и типами значений. Это помогает поддерживать порядок и снижать количество ошибок.

2. Связи между таблицами. SQL позволяет удобно работать со связанными данными. Например, один клиент может иметь несколько заказов, которые связаны через внешний ключ (Foreign Key).

3. Поддержка транзакций ACID. Реляционные СУБД хорошо подходят для финансовых операций и других задач, где важны согласованность и целостность данных.

4. Сложные запросы. С помощью SQL можно объединять таблицы (JOIN), выполнять фильтрацию, группировку и аналитические расчёты.

5. Стандартизированный язык запросов. SQL поддерживается большинством реляционных СУБД, например PostgreSQL, MySQL и Microsoft SQL Server. Это упрощает изучение и перенос знаний между системами.

### 3.1.* Преимущества NewSQL перед SQL и NoSQL

**Ответ:**

NewSQL — это класс современных СУБД, которые сочетают реляционную модель и SQL с возможностями распределённой архитектуры.

К преимуществам NewSQL можно отнести:

1. Горизонтальное масштабирование. Можно распределять хранение и обработку данных между несколькими серверами.

2. Поддержку SQL. Разработчики могут использовать привычный язык SQL для работы с данными.

3. Транзакции ACID. NewSQL стремится сохранять надёжность транзакций даже при распределении данных между узлами.

4. Отказоустойчивость. Некоторые NewSQL-системы автоматически реплицируют данные и продолжают работу при отказе отдельных серверов.

5. Высокую производительность при больших нагрузках. Распределённая архитектура может обрабатывать значительное количество одновременных запросов при правильном проектировании.

## Задание 4. Кластеры

Условие: необходимо выполнять большое количество вычислений над огромными объёмами данных. Для этой задачи выделено 1000 машин.

**Ответ:**

В данном случае я бы выбрал распределённую систему обработки данных, которая позволяет использовать вычислительные ресурсы всех 1000 серверов.

Основными критериями выбора будут:

- Возможность горизонтального масштабирования.

- Распределение данных и вычислений между серверами.

- Отказоустойчивость при выходе из строя отдельных узлов.

- Поддержка параллельной обработки больших объёмов данных.

- Минимизация передачи данных между серверами.

Для хранения и аналитической обработки можно рассмотреть распределённые аналитические системы, например ClickHouse, в зависимости от характера запросов.

Для выполнения сложных распределённых вычислений я бы выбрал Apache Spark, используя распределённое хранилище, например HDFS или объектное хранилище.

### Какая модель распределённых вычислений подойдёт?

Для пакетной обработки больших данных подходит модель MapReduce.

Она работает по следующему принципу:

1. Map — большая задача разделяется на части, которые обрабатываются параллельно на разных серверах.

1. Shuffle — промежуточные результаты перераспределяются и группируются.

1. Reduce — частичные результаты объединяются в общий результат вычислений.

Apache Spark поддерживает похожие распределённые операции, но не ограничивается классической схемой MapReduce и может выполнять более сложные цепочки вычислений.
